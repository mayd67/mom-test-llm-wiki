# 测试用例评审维度

## 一、核心评审维度

| 维度 | 核心问题 | 常见问题类型 |
| --- | --- | --- |
| 覆盖完整性 | 需求、RPD、原型里的关键规则是否都有对应测试用例 | 漏主流程、漏异常、漏边界、漏权限、漏状态 |
| 业务正确性 | 用例理解的业务规则是否与原文一致 | 预期写错、字段口径错、状态流转错、规则条件错 |
| 粒度拆分 | 一条用例是否只验证一个明确目标 | 多个目标混一条、步骤过长、无法定位失败点 |
| 可执行性 | 用例是否能被测试人员直接执行 | 前置缺失、步骤抽象、数据不足、入口不清 |
| 可验证性 | 预期结果是否可观察、可断言 | 只写“成功”“正常”，没有状态、字段、提示或数据结果 |
| 追踪关系 | 能否从需求/RPD追到测试用例 | 缺编号、缺标签、章节映射不清 |
| 优先级合理性 | P0/P1/P2 是否与业务风险匹配 | 主流程定太低、低频提示定太高 |
| 冗余与一致性 | 是否存在重复、冲突或命名不一致 | 多条重复覆盖同一点、同规则预期冲突 |
| 模板合规性 | 列结构、模块路径、标签、备注是否符合本地规范 | 列缺失、模块路径乱、备注无来源信息 |

## 二、重点检查顺序

1. 先看主流程和阻断型规则是否漏测。
2. 再看异常、边界、权限、状态流转是否被拆开覆盖。
3. 再看步骤和预期是否能执行、能验证。
4. 最后看优先级、命名、模板字段和重复项。

## 三、按功能描述逐项评审

当需求文档的每个功能点都按固定小节展开时，优先按下面顺序逐项拆评审点：

| 需求小节 | 评审重点 | 常见漏项 |
| --- | --- | --- |
| 功能目标 | 用例是否真的验证了该功能点的核心目标 | 只测页面打开，不测真正业务动作 |
| 适用角色 | 是否覆盖正确角色和错误角色 | 漏角色差异、漏权限限制 |
| 前置条件 | 是否准备了必需状态、数据、配置 | 缺工作流配置、缺已发布数据、缺来源对象 |
| 触发方式/操作步骤 | 用例步骤是否与需求触发路径一致 | 漏入口、路径不一致、把多个动作混一起 |
| 系统处理逻辑 | 每条关键规则是否有明确断言 | 只测最终成功，不测校验、状态变化、自动处理、排除逻辑 |
| 输出结果 | 是否验证状态、字段、列表、回写、重算结果 | 只写“保存成功”，不校验具体结果 |
| 异常处理/边界处理 | 是否有对应负向或边界用例 | 漏提示文案、漏非法状态、漏恢复限制 |
| 涉及页面/入口 | 是否覆盖正确页面和入口差异 | 菜单入口与穿透入口混淆 |
| 补充说明 | 只读字段、默认值、限制条件是否落入用例 | 漏只读校验、漏“不可编辑/不可恢复/不参与统计” |

## 四、发现项分类建议

| 类型 | 说明 |
| --- | --- |
| 漏覆盖 | 需求规则存在，但没有对应测试用例 |
| 误覆盖 | 看似有用例，实际验证对象或预期与需求不一致 |
| 混目标 | 同一条用例混入多个验证目标，失败时无法定位 |
| 不可执行 | 前置、步骤、数据、入口描述不足，无法实际执行 |
| 不可验证 | 预期结果太空泛，无法判断通过失败 |
| 规则漏断言 | 需求写了系统处理逻辑或输出结果，但用例没有对应断言 |
| 优先级失真 | 用例等级与风险不匹配 |
| 重复冗余 | 两条或多条用例本质覆盖相同验证点 |
| 模板问题 | 列结构、模块路径、标签、备注不符合模板口径 |
| 待确认 | 源材料本身不清晰，无法给出确定结论 |

## 五、严重级别建议

| 级别 | 适用情况 |
| --- | --- |
| 高 | 主流程漏测、关键业务规则理解错误、核心状态/权限错误、会导致假通过或阻断上线 |
| 中 | 常见异常或边界漏测、系统处理逻辑未落断言、前置条件不足、粒度不合理、优先级明显不当 |
| 低 | 命名、模块路径、标签、备注、格式等规范性问题 |

## 六、输出规则

- findings 放在最前面。
- 一条 findings 只写一个问题。
- 每条 findings 尽量同时给出：需求/RPD依据、对应用例、问题说明、建议修订。
- 如果评审对象是本地文件，优先给出文件路径和行号引用。
- 如果源材料本身有歧义，不要硬判错，转入 `待确认信息`。
