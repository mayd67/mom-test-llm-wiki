# User Manual Writer

在编写、补写、改写或统一 MOM 用户操作手册时使用这个 skill。

## 工作流程

1. 统一输入材料。
- 优先读取现有 `wiki/05_产品操作手册/docs/` 里的同类页面，先对齐当前手册风格。
- 再读取对应功能的需求文档、设计页、操作路径说明、工作台或模块页面。
- 如用户提供了截图、原型图或录屏讲解稿，也一并纳入。

2. 确定手册定位。
- 判断目标文档是面向新用户、业务人员、实施/运维、测试、培训还是交付。
- 判断输出是“模块操作说明”“功能说明”“快速上手页”“FAQ 页”还是“培训讲稿型手册”。
- 未明确时，默认输出为面向业务用户的模块操作说明。

3. 组织手册结构。
- 默认保持和现有产品手册一致的写法：功能概述、前置条件、操作步骤、注意事项、结果说明、补充说明。
- 若是模块级正文，优先采用：
  - `## 功能概述`
  - `## 操作前置条件`
  - `## 核心功能`
  - `## 操作指南`
  - `## 注意事项`
- 若是首页或总览页，优先采用导航式结构，而不是逐步操作结构。

4. 编写正文。
- 步骤必须可执行，菜单路径、按钮名称、字段名称尽量与现有 wiki 页面一致。
- 对同一页面的多个按钮或入口，分小节展开，不要混写。
- 如果输入材料不足以确认字段、按钮、状态或规则，不要编造，直接写成“待补充”或省略不确定细节。
- 用户用中文提问时，默认输出中文。

5. 处理截图与界面说明。
- 如果已有截图，但用户没要求插图落盘，可先在正文中写 `![截图说明](images/xxx.png)` 占位建议。
- 如果没有截图，也可以在对应步骤后写一句“建议补充页面截图：xxx 区域”，方便后续补图。
- 不要臆造图片文件名；只有在当前目录已有图片时，才引用真实路径。

6. 输出结果。
- 默认输出为 Markdown 正文。
- 若目标是直接沉淀到知识库，优先对齐 `wiki/01_MOM产品相关文档/05_产品操作手册/docs/` 现有结构和命名方式。
- 若用户只要某个功能章节，可只输出章节正文，不强行生成整本手册。

## 编写规则

- 先解释“这个功能做什么”，再写“怎么操作”。
- 一个步骤只描述一个清晰动作，避免把多个动作塞进同一行。
- 尽量用产品中的真实菜单名、按钮名、字段名。
- 注意区分“系统自动行为”和“用户手工操作”。
- 注意区分“前置配置”“操作步骤”“操作结果”“异常说明”。
- 如内容来自需求或设计而非现网手册，要避免写成“已经存在的界面能力”口吻；必要时注明“按当前资料”。

## MOM 手册补充规则

- 管理平台、工作台、配置中心、业务配置这类多入口功能，要明确入口差异。
- 涉及角色、权限、工作中心、组织、工厂时，要补充使用前提。
- 涉及报工、报检、质量填报、任务协调、异常报警等执行型功能时，要优先写清状态前置条件和数据流向。
- 涉及导入、导出、打印、审批、附件上传、扫码、批量操作时，要补充常见限制和注意事项。
- 如同一功能已有讲稿、视频脚本或培训材料，优先与其口径保持一致。

## 追问与推断规则

- 只有当连目标模块或目标文档类型都无法识别时，才追问用户。
- 如果材料不完整但仍可写出初版，就先输出初版，并显式保留缺口。
- 不要虚构按钮、字段、接口返回、状态值或权限矩阵。

## 典型触发语

- “生成这个模块的用户操作手册”
- “根据需求和截图写操作说明”
- “补一页产品手册”
- “把这个功能改写成面向用户的操作手册”
- “整理成交付培训可用的模块说明”
