# 业务方案与PRD生成端到端测试用例指南

本文档用于说明：如何把 `业务方案 + PRD + 设计资料` 转换成一份业务场景驱动的端到端测试用例。

这里的“端到端测试用例”默认等价于：

- UAT 场景用例
- 业务闭环场景用例
- 跨角色、跨模块的 E2E 用例

它不是页面按钮级功能用例，也不是直接用于 Playwright / Selenium 编码的自动化脚本说明。

## 一、一句话原则

业务方案定场景，PRD 定功能和规则，设计资料定数据和联动；先形成 E2E 测试点，再展开成 E2E 测试用例。

## 二、适用范围

适合使用本方法的场景包括：

- 需要验证从起点单据到终点结果的业务闭环
- 涉及多个角色接力操作
- 涉及多个模块、对象或上下游系统联动
- 需要输出 UAT、联调或验收阶段的场景用例

不适合直接套用本方法的场景包括：

- 单页面字段校验
- 单按钮功能验证
- 只关注接口入参和返回值的技术测试
- 直接产出自动化脚本代码

## 三、概念边界

| 类型 | 主要回答的问题 | 典型粒度 | 主要输入 |
| --- | --- | --- | --- |
| 端到端场景用例 | 一条业务链路能否完整跑通 | 一个业务目标 / 一条闭环 | 业务方案 + PRD + 设计资料 |
| 功能测试用例 | 某个功能点和规则是否正确 | 一个页面动作 / 一条规则 | PRD + 设计资料 |
| UI 自动化用例 | 哪些高频稳定场景适合持续回归 | 稳定且可重复的操作路径 | 已评审 E2E / 功能用例 |

一句话区分：

- E2E 用例先解决“业务闭环是否成立”
- 功能用例解决“局部功能和规则是否正确”
- UI 自动化解决“哪些稳定场景值得持续回归”

## 四、输入材料与职责分工

| 材料来源 | 重点提取内容 | 在 E2E 用例中的作用 |
| --- | --- | --- |
| 业务方案 | 业务目标、场景边界、参与角色、上下游系统、闭环标准 | 决定场景清单和主链路 |
| PRD | 页面入口、操作步骤、字段规则、状态变化、验收标准 | 把场景补成可执行步骤 |
| 研发设计文档 | 数据模型、接口、状态机、回写规则、异常处理 | 补数据校验、联动和边界 |
| 操作手册 / 原型 | 实际菜单路径、页面路径、按钮文案 | 补执行路径和页面口径 |
| 历史缺陷 / 测试经验 | 高频失败点、串联断点、典型风险 | 补异常场景和回归点 |

推荐读取顺序：

1. 业务方案
2. PRD
3. 设计文档 / 数据模型 / 接口说明
4. 操作手册 / 原型
5. 历史缺陷与测试资料

## 五、标准生成流程

```text
业务方案
-> 提取端到端场景清单
-> 用 PRD 补页面和操作细节
-> 用设计资料补数据、状态、接口联动
-> 形成 E2E 测试点
-> 评审测试点
-> 生成 E2E 测试用例
-> 评审用例
-> 视需要筛选自动化候选场景
```

### 1. 从业务方案提取“场景卡片”

每张场景卡片至少写清楚：

- 场景名称
- 触发事件
- 起点角色
- 终点结果
- 涉及模块
- 关键对象
- 上下游系统
- 成功闭环标准

如果连这 8 项都无法明确，就不要直接生成完整用例，应先列为待确认项。

### 2. 用 PRD 补成“可执行链路”

重点补以下内容：

- 菜单入口和页面入口
- 具体操作顺序
- 参数、字段、选择项
- 页面提示和中间状态
- 业务规则和验收结果

此阶段的目标，是把“业务场景”补成“人能照着走完的路径”。

### 3. 用设计资料补“可验证结果”

重点补以下内容：

- 数据对象和关联关系
- 状态流转
- 接口触发和回写
- 异常阻断点
- 跨模块联动结果

此阶段的目标，是让“期望结果”不只停留在页面成功提示，而能覆盖数据和状态。

### 4. 先形成 E2E 测试点，再写测试用例

推荐先按 [[测试点生成与评审流程]] 生成一份 E2E 测试点，再按 [[测试用例生成与评审流程]] 展开成用例。

原因：

- 测试点先确认“测什么”
- 测试用例再确认“怎么测”

如果直接从材料一步生成完整 E2E 用例，容易出现：

- 场景粒度过大
- 角色链路缺失
- 只写页面步骤，不写联动结果
- 多条场景重复叠加在同一用例里

## 六、场景拆分规则

一条端到端用例，建议只覆盖一条明确的业务闭环。

建议按以下维度拆分：

- 一个业务目标一条主成功路径
- 一个关键角色链路一条主成功路径
- 一个关键异常阻断点单独成条
- 一个明显不同的分支路径单独成条
- 一个权限差异路径单独成条

常见拆分结果通常包括：

- 主成功路径
- 替代成功路径
- 阻断异常路径
- 权限差异路径
- 关键回归路径

不要把以下内容混成一条超长用例：

- 多个业务闭环
- 多个起点单据
- 多个上下游系统模式
- 多个角色完全独立的操作路径

## 七、从材料到模板字段的映射

以下字段映射适用于用户提供的《端到端场景测试用例模板》。

| 模板字段 | 主要来源 | 编写建议 |
| --- | --- | --- |
| 用例编号 | 测试产物 | 按 `UAT-001`、`E2E-001` 等顺序编号 |
| 方案编号（DNW） | 业务方案 / PRD | 优先写对应方案或需求编号 |
| 角色 | 业务方案 + PRD | 写真实参与链路的角色，可多角色并列 |
| MES模块 | PRD / 操作手册 | 写主业务路径涉及的模块，不只写单页面 |
| 场景活动 | 业务方案 | 用业务动作命名，如“排程下达执行闭环” |
| 场景描述 | 业务方案 | 写业务目标，不写 UI 细节 |
| 数据样例 | 设计资料 / 测试数据 | 写订单、物料、库存、工艺、方案等关键对象 |
| 前置条件 | PRD + 设计资料 | 写权限、主数据、配置、接口连通、状态基线 |
| 操作描述 | PRD / 操作手册 | 按真实执行顺序写步骤 |
| 期望 | PRD + 设计资料 | 同时写页面结果、数据结果、状态结果、联动结果 |
| 备注/缺陷 | 历史测试资料 | 记录风险、已知限制、执行中发现的问题 |

## 八、期望结果怎么写才算合格

E2E 用例中的“期望”至少应覆盖 4 类结果：

1. 页面结果
2. 数据结果
3. 状态结果
4. 联动结果

示例：

- 页面结果：页面生成成功提示，可查询到对应单据
- 数据结果：制造任务、检验单、库存记录正确创建或回写
- 状态结果：订单 / 任务 / 单据状态按预期流转
- 联动结果：上下游模块可看到关联记录，追溯关系正确

只写“保存成功”“提交成功”通常不够，至少还要补一条数据或状态结果。

## 九、推荐输出结构

如果当前目标是人工场景测或 UAT，建议优先输出 Markdown 版场景用例。

推荐落位：

- 初稿：`outputs/03_测试用例/01_待评审/`
- 评审稿：`outputs/03_测试用例/02_已评审/`
- 如需导入平台：`outputs/03_测试用例/03_MeterSphere导入/`

推荐命名：

- `方案编号-模块名称-端到端测试用例-V1.0.md`
- `方案编号-模块名称-端到端测试用例-MeterSphere导入-V1.0.xlsx`

目录规则统一参考 [[测试交付物目录规范]]。

## 十、是否适合直接做 UI 自动化

默认不建议把场景模板直接当成 UI 自动化脚本输入。

更稳妥的做法是：

1. 先形成业务场景用例
2. 再从中筛选自动化候选场景
3. 最后补自动化执行所需信息

适合自动化的场景通常具备以下特征：

- 流程稳定，不频繁改版
- 测试数据可重复准备
- 页面路径稳定，控件定位稳定
- 断言点明确，不依赖人工判断
- 执行成本高，回归频率高

不适合优先自动化的场景通常包括：

- 依赖大量人工准备数据
- 强依赖外部系统人工配合
- 页面频繁变更
- 结果判断依赖人工主观结论

## 十一、常见误区

### 1. 只看 PRD 就直接写 E2E

结果通常会退化成页面功能用例，缺少业务闭环和上下游联动。

### 2. 只写页面操作，不写数据与状态

结果通常只能支持人工点点看，不能作为高质量验收依据。

### 3. 一条用例塞入多个闭环

结果会导致前置条件过重、执行成本高、失败后难定位问题。

### 4. 不区分场景测与自动化

结果会把业务语言、执行步骤、自动化断言混在一起，既不利于业务验收，也不利于脚本实现。

### 5. 不先做测试点，直接批量出用例

结果容易出现重复、漏链路、漏异常和角色边界不清。

## 十二、可直接复用的提问模板

当你需要让 LLM 基于材料生成 E2E 用例时，可以直接给出如下提示词：

```text
你是 MOM 测试分析师。

请根据以下输入材料：
1. 业务方案
2. PRD / 产品需求文档
3. 如有则补充设计文档、数据模型、接口说明
4. 端到端场景测试用例模板

生成“业务场景驱动”的端到端（E2E/UAT）测试用例。

要求：
1. 不按页面功能拆分，而按业务闭环场景拆分。
2. 每条用例必须覆盖：触发条件、角色接力、跨模块流转、关键数据对象、状态变化、最终业务结果。
3. 优先输出主成功路径，再补充关键异常路径和权限差异路径。
4. 每条用例输出以下字段：
- 用例编号
- 方案编号（DNW）
- 角色
- MES模块
- 场景活动
- 场景描述
- 数据样例
- 前置条件
- 操作描述
- 期望
- 备注/缺陷
5. 期望结果必须同时包含：
- 页面表现
- 数据落库或回写
- 状态流转
- 关联单据或上下游联动
6. 如果输入材料不足以支持 E2E 判断，明确列出待确认项，不要臆造。

输出格式：Markdown 表格。
```
