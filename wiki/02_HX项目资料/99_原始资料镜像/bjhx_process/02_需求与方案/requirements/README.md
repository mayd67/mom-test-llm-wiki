### 需求代号规则

- 采用5位数字格式，固定长度，不足位前补零
- 每次递增10（如 00010、00020、00030...）
- 预留中间编号（如 00011-00019）用于后续插入补充需求或紧急需求
- 口头沟通时可简称为"10号需求"，正式文档须写全编号

### 各子目录说明

#### _templates/ — 模板与编写参考

存放当前仓库统一采用的需求模板、章节骨架和编写参考。模板属于公共资产，不放入单个 `REQ-xxxxx` 目录，避免与具体需求材料混放。

#### datamodels/ — 需求编制的数据模型输入

需求文档编制时，除读取 `original/`、`process/` 中的原始材料与过程材料外，还应读取同级 `../datamodels/` 目录中的数据模型资料，用于统一模型命名口径、识别已有标准能力与项目扩展能力，并提高需求描述与现有系统实现的符合性。

推荐读取顺序：

1. `../datamodels/README.md`
2. `../datamodels/product-standard/README.md`
3. `../datamodels/project-extension/README.md`
4. `../datamodels/project-extension/project-datamodels/` 中与当前需求相关的项目数据模型文档

使用原则：

- 产品标准数据模型以正式标准模型文档为准，本项目目录中的 `product-standard/README.md` 仅用于记录权威来源与引用约定。
- 项目扩展数据模型以 `../datamodels/project-extension/source-json/` 为事实来源，以 `project-datamodels/` 中的 `md` 文档为阅读引用版本。
- 需求文档只摘录与当前需求直接相关的模型、属性、关系，不重复抄写完整数据模型正文。
- 如需求中涉及的数据项在现有模型资料中未找到，应在 `process/` 中记录为待确认项，不应直接主观补造。

#### original/ — 原始需求材料

存放客户/交付提供的原始需求文档，原样保留，不做修改。

**文件命名规范**：`YYYYMMDD_内容描述.格式后缀`

| 元素 | 说明 | 示例 |
|------|------|------|
| YYYYMMDD | 材料收集/接收日期 | 20260424 |
| 内容描述 | 简明概括材料内容 | 火鸡品管理功能-原始需求 |
| 格式后缀 | 原始格式保留 | .docx、.pdf、.png、.mp4 |

#### process/ — 需求编制过程记录

存放需求分析、确认、评审、变更等过程中的产物。

**常见文件类型**：

| 文件类型 | 命名示例 | 说明 |
|---------|---------|------|
| 疑问清单 | `20260424_疑问清单.md` | 原始需求中不明确、需要确认的点 |
| 客户确认记录 | `20260425_客户确认记录.md` | 与客户沟通后的确认结果 |
| 评审纪要 | `20260426_需求评审纪要.md` | 内部评审会议的结论和修改意见 |
| 变更记录 | `20260428_变更说明_v1.0→v1.1.md` | 需求变更的原因、内容、影响 |
| 参考资料 | `20260424_类似系统调研.md` | 编制过程中参考的外部资料 |

存放编制完善后的需求规格说明书，作为项目开发、测试、验收的基准文档。

**文件命名**：`REQ-xxxxx_需求名称.md`

### 跨需求材料处理

若一份原始材料涉及多个需求，按以下方式处理：

1. **首选**：在主要关联的需求目录的 `original/` 中放置原件，其他需求目录中创建 `_引用说明.md` 指向原件位置
2. **次选**：若材料可明确拆分（如文档的不同章节），可在各需求目录的 `original/` 中放置标注了相关章节的副本

### 新增需求步骤

1. 在 `index.md` 中登记新需求（分配代号、填写名称和业务单元）
2. 创建目录：`mkdir REQ-xxxxx_需求名称`
3. 在目录内创建 `original/`、`process/`、`finalized/` 三个子目录
4. 将原始材料放入 `original/`，并创建 `_index.md`
5. 在编制需求前，先读取 `../datamodels/` 下与当前需求相关的数据模型资料，识别标准模型引用范围、项目扩展属性、项目新增模型及关系
6. 在 `process/` 中记录编制过程，以及需求与数据模型之间的待确认问题、口径确认结果和变更记录
7. 在 `finalized/` 中编写最终需求文档，并在 `2.4 数据描述`、`2.7 接口需求`、`3. 影响范围分析` 等章节中引用已确认的数据模型口径

### 需求编制建议流程

为保证需求文档与现有产品标准能力、项目模型现状保持一致，建议按以下顺序编制：

1. 阅读 `original/` 中原始材料，理解业务目标、场景和问题背景
2. 阅读 `process/` 中已有记录，识别已确认事项、未决问题和历史结论
3. 阅读 `../datamodels/` 中相关模型资料，确认本需求涉及的标准模型、项目扩展属性和项目新增模型
4. 建立“功能点 - 数据模型”映射，至少识别：
   - 涉及哪些模型
   - 使用哪些关键属性
   - 是否存在已有项目扩展
   - 是否需要新增扩展或新增模型
5. 依据模板编写 `finalized/` 正式需求文档
6. 编写完成后，检查需求中的模型名、属性名、关系名、接口字段名是否与数据模型资料一致

### 数据模型一致性检查建议

需求文档完成后，建议至少检查以下事项：

- `2.4 数据描述` 中引用的模型名、属性名、关系名是否与正式数据模型口径一致
- 是否把项目扩展属性误写成产品标准能力
- 是否遗漏了当前需求实际依赖的项目新增模型或关系模型
- `2.3 功能描述` 中的数据变化是否能在 `2.4 数据描述` 找到对应模型支撑
- `2.7 接口需求` 中输入输出字段是否能在已确认模型中找到来源或去向
- 如存在模型缺口、命名冲突或来源不明项，是否已在 `process/` 中形成待确认记录
