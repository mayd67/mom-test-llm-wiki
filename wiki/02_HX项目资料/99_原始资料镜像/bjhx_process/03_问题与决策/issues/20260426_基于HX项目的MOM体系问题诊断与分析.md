### 一、部署运维

#### 1.1 问题全景

部署一套完整的MOM系统涉及组件众多、配置项繁杂，这是部署运维问题的根本原因。当前的问题呈现为一条因果链：

```
组件多、配置繁（根因）
  → 环境变量命名不统一、公共配置重复填写（症状：理解维护成本高，疏漏导致运行异常）
  → 端口冲突频发（症状：启动失败，需人工排查）
  → 部署效率低、出错率高（结果）
```

解决思路：**标准化 → 自动化**。先统一规范，再基于规范实现自动化部署，从根本上降低复杂度。

#### 1.2 部署复杂度高

部署一套完整的MOM系统涉及：MOM前端、MOM后端9+个应用服务、7种中间件、运行态前端、运行态后端、二次扩展开发后端，配置项繁多，部署复杂度高，对部署人员要求较高。

#### 1.3 环境变量与配置不统一

运行态、二开、MOM后端等各组件的启动环境变量（如 `-DNACOS_ADDR` 等）命名和配置方式不统一，增加理解和维护成本。同时，数据库、文件服务等公共配置项在各组件中需要重复配置，一旦疏漏会导致运行异常。

#### 1.4 端口冲突导致启动失败

部署时经常出现端口被占用的情况，导致应用服务启动失败，需要人工排查端口占用并手动处理，增加部署时间和出错概率。

#### 1.5 改进方向

1. **推进部署标准化**：统一环境变量命名规范、抽取公共配置为共享配置，为自动化部署奠定基础
2. **增加端口预检功能**：启动前自动检测目标端口是否被占用，若被占用则给出明确提示和处理建议
3. **提供部署检查清单**：确保关键配置项无遗漏
4. **制作部署演示视频和常见FAQ**：降低部署学习门槛

### 二、产品协同与信息同步

#### 2.1 问题全景

MOM 3.x系统实施涉及MOM产品、低代码平台、二次开发、项目交付等多个团队，核心矛盾是**产品与项目之间信息不对称**，表现为三个层面：

```
信息不对称（根因）
  → 产品变更不通知项目（被动受损：功能异常、数据不一致）
  → 新功能/变更交付不知情（能力断层：无法使用新能力）
  → 多方沟通机制缺失（机制问题：信息无法及时触达所有相关方）
```

解决思路：**建立变更通知机制 + 信息发布机制**，从流程上保障信息对称。

#### 2.2 产品变更未通知项目组

产品侧对数据模型、功能进行变更时，未提前通知项目组，项目组无法评估变更对现有业务的影响，导致项目直接受影响，出现功能异常或数据不一致等问题。产品变更前应先向相关项目组了解使用情况，评估变更影响范围，并给出兼容方案或迁移路径。

#### 2.3 产品功能文档与演示视频不完善

现场交付人员对产品新功能和变更后的功能不了解，缺乏及时知情的渠道。现有问题包括：

1. 产品功能演示视频和操作手册不完善，新功能缺乏配套文档
2. KMTube（基于PeerTube搭建的视频平台）上已有视频管理混乱，存在文件名和标题不规范的情况（如 `meeting_01` 这类无法理解内容的标题），无法快速定位所需视频
3. 视频未按产品、模块分类管理，检索困难

#### 2.4 多方沟通机制不畅通

当某一方发生变更或推出新特性时，信息无法及时同步到所有相关方，导致其他团队被动受影响。缺乏跨团队的信息同步机制，产品变更、新特性发布、重要决策等信息无法及时触达所有相关角色。

#### 2.5 改进方向

1. **建立产品变更通知机制**：数据模型和功能变更前，必须通知相关项目组并评估影响，确保变更可控
2. **建立信息发布机制**：可考虑定期同步会议、变更通知群、信息发布看板等方式，确保信息及时触达
3. **完善产品功能文档**：新功能上线时同步产出演示视频和操作手册
4. **规范KMTube视频管理**：规范命名和标题，按产品、模块分类管理
5. **定期发布功能清单**：建议每1-2个月整理发布功能清单及对应演示视频，保持交付团队对产品能力的持续了解

### 三、低代码平台

#### 3.1 集成能力不清楚

低代码平台的集成能力不清楚，交付团队不确定低代码平台是否支持对接集成平台进行数据集成，也不清楚是否支持Excel作为数据输入方式。由于对平台能力认知不足，项目上倾向于额外开发对接工作，增加了开发与维护成本。

**期望改进**：

1. 明确低代码平台的集成能力边界，形成能力说明文档
2. 若支持对接集成平台，提供配置化集成方式的操作指南
3. 若支持Excel数据输入，提供使用说明；若不支持，明确排期

#### 3.2 页面渲染延迟

低代码页面打开后存在明显的渲染延迟，页面空白数秒后才显示内容，用户体验较差，客户对此反馈强烈。

**期望改进**：优化低代码页面的加载和渲染性能，减少白屏时间。建议从资源加载策略、组件懒加载、渲染链路优化等方面排查改进。

### 四、日志规范

#### 4.1 问题全景

MOM项目实施由产品、低代码平台、二次扩展三部分组成，日志问题呈现为一条因果链：

```
日志格式不统一、缺少结构化规范（根因）
  → 只能通过supervisor查看日志，缺少结构化、检索和界面化能力（症状）
  → 客户和交付排查问题门槛高、效率低（结果）
```

解决思路：**先统一格式，再提供工具**。结构化是前提，有了结构化日志才能构建界面化的检索查看能力。

#### 4.2 统一结构化日志

MOM项目实施由产品、低代码平台、二次扩展三部分组成，三者的程序日志、集成日志格式不统一，缺乏结构化规范，导致交付人员和客户在排查问题时难以快速定位根因。

**期望改进**：三者的程序日志和集成日志统一采用结构化格式（如统一的JSON结构），包含时间戳、级别、模块、链路ID等关键字段，便于日志检索、链路追踪和问题排查。

#### 4.3 日志查看方式不友好

当前排查问题只能通过supervisor查看日志，缺少结构化、检索和界面化能力，对客户和交付均不友好：

- **客户侧**：客户不具备服务器操作能力，问题反馈后只能等待供应商排查，响应周期长，客户体验差
- **交付侧**：日志缺少结构化格式和检索能力，排查问题需逐个翻看原始日志，效率低；多组件日志分散，排查链路长
- **协作侧**：客户与交付之间缺乏可共享的日志查看手段，问题沟通依赖截图/复制文本，信息易丢失、难追溯

**期望改进**：提供日志查看的界面化工具或平台，使客户和交付人员无需登录服务器即可检索和查看日志，降低问题排查门槛。

### 五、二次开发

#### 5.1 二次开发资源不足

二次开发扩展资源严重不足，目前仅杨勇一人承担二开工作，无法满足项目需求，资源瓶颈已影响项目正常推进。

**期望改进**：

1. 优先保障项目关键路径的二开需求，确保项目正常推进
2. 二开任务的Jira故事需与项目任务单关联，确保优先级与项目计划对齐
3. 评估增加二开资源的可行性，缓解单点依赖风险

**处理结果**：优先保障项目交付进度，暂停产品和低代码（除集成部分外）的新功能开发。
