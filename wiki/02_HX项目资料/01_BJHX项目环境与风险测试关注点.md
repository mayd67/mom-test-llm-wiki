# BJHX项目环境与风险测试关注点

## 一、环境事实

- 服务器规模：4 台物理服务器 A/B/C/D。
- 统一基础环境：`海光 C86`、`256GB` 内存、`麒麟 V10SP3`、纯内网、物理部署。
- A/B 服务器规划：达梦主备 + `RUSTFS` 文件柜。
- C 服务器规划：最新 MOM 版本，后续承接中间件。
- D 服务器现状：当前演示环境，需保持稳定。

## 二、对测试影响最大的项目约束

| 约束 | 影响 | 测试关注点 |
| --- | --- | --- |
| 无独立测试环境 | 验证机会受限 | 需要明确测试窗口、冒烟范围、回滚预案和证据留存方式 |
| HBA 卡未到位 | 存储方案分阶段落地 | 当前验证结果只覆盖临时方案，后续迁移仍需专项回归 |
| 中间件待从 D 迁移到 C | 环境角色会变化 | 需关注中间件迁移后的连通性、配置完整性和旧环境残留 |
| 纯内网 + 物理部署 | 工具链和排障成本较高 | 日志、脚本、依赖包、浏览器和附件链路都要提前准备 |
| 项目含二开与产品协同 | 缺陷归因复杂 | 需区分产品变更、配置错误、低代码问题、二开问题 |

## 三、阶段性 Top 风险

- 无独立测试环境，导致系统验证活动受限。
- HBA 卡未到位，共享存储与后续迁移方案尚未完全落地。
- HGP 类高定制需求时间紧，容易压缩测试准备和回归窗口。
- 检查项填报与质量方案关联链路发生产品侧变化，存在业务断链风险。
- 批量汇报属于现场高优先级需求，交付时间靠近试运行准备期。

## 四、系统性问题模式

根据 `20260426_基于HX项目的MOM体系问题诊断与分析.md`，以下问题模式值得作为长期测试关注点：

### 1. 部署与配置问题

- 环境变量命名不统一。
- 公共配置重复填写，容易遗漏。
- 端口冲突导致启动失败。

测试含义：

- 部署验证不能只看“服务是否启动”，还要做配置完整性核对和端口预检。
- 升级、补丁、环境切换后的回归要覆盖配置继承与兼容。

### 2. 产品变更未同步项目

- 数据模型、功能规则可能先变更，项目侧后知后觉。
- 典型案例就是质量填报模板改由质量方案间接关联。

测试含义：

- 每次版本变化后，都要补做受影响模块的链路回归。
- 发现“以前好用、这次断了”的问题时，优先怀疑产品规则变化和兼容缺口。

### 3. 低代码能力与性能问题

- 集成能力边界不清楚。
- 页面渲染存在白屏或明显延迟。

测试含义：

- 需求验收时不仅要测功能结果，还要测首屏加载、渲染稳定性和跨模块集成可行性。

### 4. 日志规范不足

- 多组件日志格式不统一。
- 仅能通过 supervisor 原始查看，缺少结构化检索。

测试含义：

- 高风险场景应提前约定日志采集口径。
- 缺陷复现记录里最好同时保留页面现象、接口/服务日志、关键参数和时间点。

## 五、建议验证策略

以下内容是基于当前项目资料推导出的测试建议：

- 先准备“最小可执行验证清单”，避免在无独立测试环境下把验证目标铺得过大。
- 对部署类变更，按“服务启动、核心链路、日志、数据、回滚”五步做验证。
- 对迁移类操作，必须保留迁移前基线、迁移后冒烟结果和异常回滚路径。
- 对二开需求，要求至少形成“业务演示数据 + 异常数据 + 回归数据”三组样本。
- 对问题排查，优先保留操作时间、操作人、任务/单据编号、服务节点和日志片段，降低多人协作时的信息损耗。

## 六、优先回归范围

- 工序汇报、质量方案、检查项填报之间的联动链路。
- 仓储、库存、出入库、基础数据之间的数据一致性。
- C/D 服务器角色变化后的系统可用性。
- 达梦主备、文件柜临时方案、存储迁移后的数据完整性。
